# Процесс работы с задачами (GitHub Projects)

Задачи ведутся на доске GitHub Projects **«cowrie-digest — Tasks»**
(владелец: `W0nIE`). Разработка идёт по спецификации (spec-driven design):
сначала issue-спецификация, потом реализация.

## Статусы

Поле Status (single-select), порядок на доске:

`New → Analysis → Ready for dev → Dev in Progress → Testing → Review → Done`

## Зоны ответственности

| Статус | Кто работает |
|---|---|
| New | hermes создаёт issue-спецификацию по команде пользователя |
| Analysis | пользователь / другой агент (hermes здесь НЕ работает) |
| Ready for dev | пользователь переводит задачу после анализа |
| Dev in Progress | hermes (по явной команде пользователя) |
| Testing | hermes (запуск `./test.sh`, проверка acceptance criteria) |
| Review | hermes создаёт PR с `Closes #N`, пользователь ревьюит |
| Done | ТОЛЬКО пользователь |

## Жизненный цикл

1. **Приём задачи** (команда «создай задачу»): hermes создаёт issue по
   шаблону «Задача» (`.github/ISSUE_TEMPLATE/task.md`), добавляет в проект
   со статусом **New**. Реализация не начинается.
2. **Analysis**: пользователь (или другой агент) уточняет спецификацию,
   затем переводит задачу в **Ready for dev**.
3. **Разработка** (по явной команде пользователя): hermes переводит задачу в
   **Dev in Progress**, создаёт ветку, реализует. Коммиты ссылаются на issue:
   формат `#N краткое описание`.
4. **Тестирование**: задача → **Testing**. hermes запускает `./test.sh`,
   проверяет acceptance criteria из issue, результаты публикует
   комментарием в issue. Проблемы исправляются в той же ветке.
5. **Review**: задача → **Review**. hermes создаёт PR с `Closes #N` в
   описании и уведомляет пользователя.
6. **Done**: выставляет только пользователь.

## Правила

- hermes не переводит задачи в/из **Analysis** и не выполняет там работы.
- hermes никогда не выставляет **Done**.
- hermes не проверяет доску без явной команды пользователя
  («проверь доску», «возьми задачи», «возьми задачу <название>»).
- hermes не мержит PR самостоятельно.
- Изменения кода — только в рамках задач из проекта.

## QA

Критерий качества — успешный запуск `./test.sh` и выполнение
acceptance criteria из issue.
